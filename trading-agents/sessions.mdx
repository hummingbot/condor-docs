A **session** is one run of a loop in **Loop** mode. It starts when you start the loop and ends when you stop it, it shuts down, or it reaches its `max_ticks` limit. Everything the agent does in that run is recorded under the session, and every executor it opens is tagged with the session's ID.

To watch and control sessions in the Workspace or Telegram, see [Managing Agent Sessions](/getting-started/sessions).

## Session IDs

Each run gets an ID made from the agent, the loop and a number:

| Run | ID format | Example |
|---|---|---|
| Loop session | `{agent}.{loop}_{N}` | `market_making_expert.pmm_mister_operator_3` |
| Dry Run or Run Once | `{agent}.{loop}_e{N}` | `market_making_expert.pmm_mister_operator_e2` |

`N` is one more than the highest number already used by that loop's sessions (or, for `_e{N}`, its dry runs).

The ID is also the `controller_id` on every executor the run creates. The risk gate refuses an executor create that doesn't carry this exact ID, so every position can be traced back to the session that opened it.

### Executors stay with the session that opened them

Because ownership follows the session ID, a new session can't see or stop the executors an earlier session opened:

- Each tick's executor and position state is fetched for the current session's ID only.
- `stop_executor` on an executor tagged with another ID is refused.

This holds after a restart too. If you stop a loop with positions open and start it again, the new session won't manage the old positions. Close or hand them over first, or use an [emergency shutdown](/trading-agents/architecture#stopping-a-loop) to wind them down before stopping.

<Note>
Bots work differently. On its first tick, a new session of the same loop adopts the still-running bots it recognizes as its own, either by name or because an earlier session of that loop recorded deploying them.
</Note>

## Dry Run and Run Once

Dry Run and Run Once each run a single tick and then stop. They don't create a session folder or a journal. Each writes one file to `loops/<loop>/dry_runs/experiment_N.md`, with the same sections as a tick snapshot (see below).

| Mode | What the risk gate allows |
|---|---|
| `dry_run` | Reads only. Every action that would change anything is refused, including routines and code. |
| `run_once` | The same per-call checks as a live loop. It can open real positions. |

Neither mode keeps a journal, so neither one triggers a drawdown pause or an emergency shutdown.

## What a session records

A loop session writes to `loops/<loop>/sessions/session_N/`. The folder layout is on the [Architecture](/trading-agents/architecture#sessions-journals-and-learnings) page; this section explains what's inside.

### journal.md

The journal is the session's running record. It has four sections:

| Section | Contents |
|---|---|
| **Summary** | One status block, rewritten each tick: last tick, status, PnL, open executors and the last action |
| **Decisions** | One line per action the agent took, plus errors, skipped ticks and refused actions with their reasons |
| **Ticks** | One line per tick: number, time, action count and a short summary of the response |
| **Snapshots** | One metrics line per tick: PnL, volume, open executors and exposure |

The sections are capped (20 lines for Decisions, 1,000 for Ticks and Snapshots). Older lines aren't deleted. They move to `journal_archive.md` beside the journal, and a marker line records what was moved.

The agent reads and writes its own journal with `trading_agent_journal_read` and `trading_agent_journal_write`.

### Snapshots

`snapshots/snapshot_N.md` is the complete record of tick `N`:

| Section | Contents |
|---|---|
| **System Prompt** | The full prompt the agent received, collapsed by default |
| **Executor State** | The session's executors at the start of the tick |
| **Risk State** | Exposure, executor count, drawdown and limits |
| **Agent Response** | The agent's reasoning and decision |
| **Tool Calls** | Each tool called, with its status and output |
| **Stats** | How long the tick took |

Condor keeps the 100 most recent snapshots per session and deletes older ones. The Workspace's **Runs** tab reads these files.

## Restarts

If Condor restarts while a loop is running, the old session is closed. It is never resumed.

- By default, the loop stays stopped. If Condor exited unexpectedly, the session is marked interrupted and the journal notes it.
- If the loop has `restart_on_boot` set (**Resume after Condor restarts** in the Start dialog, or the toggle in the **Playbook** tab), Condor starts a **fresh session** with a new number, using the loop's config as it stands at that moment.

The fresh session is a new ID, so the [executor rule above](#executors-stay-with-the-session-that-opened-them) applies.

## Learnings carry across sessions

The journal belongs to one session. `loops/<loop>/learnings.md` belongs to the loop and outlives every session.

| Section | Used for |
|---|---|
| **Market Observations** | Lessons about the market |
| **Execution Notes** | Lessons about executing trades |
| **Retired Insights** | Lessons that no longer apply |

Each new learning is checked against the existing ones and skipped if it's a near-duplicate. Each section keeps its 20 most recent entries. Every tick's prompt includes the **Market Observations** and **Execution Notes** sections; **Retired Insights** is not sent to the agent.

You can edit learnings in the agent page's **Playbook** tab or in the file itself.
